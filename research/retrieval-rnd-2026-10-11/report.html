Lumen retrieval research and verified next steps

11 October 2026 · 25 AI research assignments · Literature, local experiments and independent review

Recommendation: first repair Lumen’s measured SQLite query-plan bottleneck and cap returned context; then evaluate adaptive hybrid retrieval. Keep exact and lexical search, add an independently searchable semantic route for vocabulary mismatch, follow source-backed relationships when the task needs them, and return the smallest useful set of source spans. The most promising research contribution is how these operations are selected and budgeted together.

This is the best-supported engineering direction from this investigation, not a proven universal winner. Published results establish useful mechanisms; local tests expose concrete limitations and test a bounded typo-repair prototype. The complete proposed system, neural candidates and downstream task savings have not been benchmarked here.

Work completed by 25 AI subagents in a scientific-style research program, with at most three active at once: specialist reviews, repository and evaluation audits, a reproducible experiment, and two independent reviews. No affiliation with an external research institution is implied. Literature was checked on 11 October 2026; this is a targeted research review, not an exhaustive systematic review or a patent novelty search.

What the problem actually requires

A fast string matcher solves a different problem from finding enough evidence for an agent to act correctly. Exhaustive literal or regular-expression search remains appropriate for finding every occurrence. Inexact questions require additional vocabulary, semantic or structural signals. Larger context is not automatically better: redundant results consume attention, tokens and subsequent reasoning time.

What is already in Lumen

The inspected checkout already defaults to weighted SQLite FTS5 BM25, preserves and splits identifiers, indexes symbol-sized chunks, boosts exact symbols and paths, and appends tightly bounded one-hop call context. Embeddings are an optional alternative, not a fused retrieval route. Calling the current implementation “plain BM25” would understate the baseline. Weighted FTS5 columns are also not the same as fully field-normalized BM25F. Architecture audit; SQLite FTS5 documentation.

The useful gaps are vocabulary mismatch, query planning, reverse/multihop relationships, final context selection and incremental freshness checks. The source supports code, Markdown/MDX and structured formats; general PDF or office-document retrieval requires additional ingestion. Source details and extension points are in the architecture audit.

The proposed retrieval pipeline

  1. Preserve the request. Separate identifiers, literal strings, path constraints and filters from descriptive language. Allow the agent to submit the original query and up to two short alternate formulations in one request. Generating these variants still costs tokens, but avoids an additional hidden model round trip.
  2. Select candidate routes under a budget. Exact questions use the fast lexical route. Natural-language intent can use lexical and semantic retrieval together even when the lexical score is high. Typo-like unknown identifiers use a bounded fuzzy vocabulary route. Structural questions enable relation traversal. Begin with explicit rules and instrumentation; learn routing only after collecting representative outcomes.
  3. Fuse and refine candidates. Start with reciprocal-rank fusion as a reproducible baseline, compare calibrated score fusion, and preserve exact constraints. A small reranker is optional and only sees a bounded candidate set. Reranking cannot recover evidence missing from every candidate route.
  4. Assemble evidence, not a pile of matches. Merge duplicate ranges, retain useful parent signatures/headings, and select spans that cover different parts of the task. Treat necessary caller/callee or claim/support pairs as bundles when their usefulness depends on being read together. Keep source text, line ranges, relation provenance and revision hashes.
  5. Cap the actual response. Enforce the token/byte budget after final serialization, including metadata and formatting. Keep an independent byte backstop. Return source-versioned handles for optional expansion. A cap on related snippets alone is insufficient.
  6. Escalate only with a reason. Allow a bounded follow-up search for missing evidence; record novel evidence and the remaining budget. Budget exhaustion means unresolved coverage, not proof that no answer exists.

Experimental starting points such as 2K/4K/8K context-token budgets, one feedback round and small expansion limits are tuning choices, not published optimal constants. Compare the planner against always-on hybrid retrieval so routing mistakes cannot hide behind lower average cost.

A concrete packing experiment is to maximize weighted coverage of task facets plus a small number of verified complementary-pair bonuses, subject to the exact serialized context budget. Subtract evidence already shown. Compare this against top-k truncation, token-normalized ranking and MMR. Positive pair bonuses break ordinary diminishing returns; use a bounded heuristic and compare small cases with an optimization oracle. Facets and pair weights remain fallible predictions.

The immediate implementation should use existing infrastructure where possible: first expose independent lexical/vector candidate generation for an honest hybrid baseline. Evaluate a compact code encoder and SPLADE-Code as challengers; compare document-only expansion when update and indexing costs amortize. Putting generated words into FTS5 is an expansion baseline, not an implementation of SPLADE's learned sparse dot product.

The novel work worth pursuing is task-conditioned evidence selection and search scheduling: estimate the value of the next retrieval action in terms of missing evidence and downstream task success, then spend time and context only where it helps. Each component has prior art. This investigation does not establish publication novelty for their combination.

What was verified locally

Repository identity was verified as ory/lumen, starting HEAD 98dfa4077930551d76c9aa127d0841471027ed86. The working tree contained pre-existing edits and continued changing during research. The prototype used a frozen copy with a source manifest; production code was not edited by this team.

The original five-case retrieval catalog returned four direct hits; its vocabulary-mismatch diagnostic failed. On that tiny corpus, warm in-process retrieval measured 256–303 microseconds without relation expansion and 319–347 microseconds with it. These figures do not measure CLI startup, realistic corpus scale, or agent wall time. The small correctness suites passed. Commands, results and limitations.

The recent BM25 SWE reports cannot establish retrieval gains: 11 of 12 inspected agent transcripts never called search. The remaining Swift transcript did call it, but received roughly 763,000 characters and encountered the client's output limit. Its report label conflicts with the raw transcript and current parser, so the precise reporting cause remains unresolved. Two oversized generated Swift declarations account for about 97% of that payload. The recorded run is verified, but its exact executable was not fingerprinted; it is not a reproduction against the frozen experiment binary. This directly supports a final output cap; it does not establish a retrieval-quality result.

Larger reproducible experiment. A frozen 259-file corpus (4.83 MB) produced 12,292 chunks. Thirty source-aware synthetic queries covered exact names, typos, identifier decomposition, paraphrases and six no-answer diagnostics. Queries and algorithm parameters were fixed before scoring. These are mechanism tests, not independent held-out evidence.

The nonsense-query regression is a clear reason to avoid unconditional expansion.

The strongest verified immediate optimization is the SQLite query plan. On the same bundled SQLite 3.51.2 and database, the existing plan began with project membership and repeatedly probed full-text matches. An isolated FTS-first join-order variant searched full-text candidates first. Median warm in-process BM25 retrieval fell from 1,145 ms to 0.809 ms. The fuzzy variant took 2.206 ms after the change, including separately measured Python expansion. A separate three-repeat SQL-only probe supports the join-order diagnosis.

The two binaries returned identical captured ordered file paths, start lines, content and scores on 60 labelled requests, representing 39 unique query strings. The harness did not compare end lines, hashes, relation metadata or multi-worktree behavior. The experimental SQL patch was applied only in the isolated copy. This is a strong performance diagnosis, not evidence of a thousand-fold reduction in agent wall time.

The current rg workflow took 59.8 ms median, but includes subprocess startup, scanning and window ranking; Lumen timings are in-process and exclude final Python normalization. Do not turn these into a pure algorithm speed ratio. The index took 3.408 seconds to build with warm filesystem pages and occupied 19.58 MB including active WAL/SHM. The initial longer timing sweep was stopped; the completed run uses two calls per unique query and records the second. Medians span queries, not a stable repeated timing distribution; concurrent workloads were present.

Before shipping a plan change, compare refreshed planner statistics against explicit join order, and test selective paths, worktrees, ties, edits, common terms and supported SQLite versions. FTS-first is not necessarily optimal under every selective filter. SQLite's optimizer documentation explains why data distributions and join order matter. What would establish the winner

Use independent, repository-held-out tasks, including natural no-answer cases, and measure source regions and complete supporting-evidence sets. CodeSearchNet-style function matching alone is insufficient. ContextBench, SWE-Explore, and Agent Retrieval Bench provide complementary evaluation models; their labels and sampling biases must be retained rather than treated as interchangeable.

Freeze a development split and a separate held-out set before tuning. Start with at least 200 real tasks across multiple repositories for a pilot, then size the confirmatory study from observed variance and the minimum useful effect. Compare a competent rg-equipped agent, current Lumen, always-on hybrid, planned hybrid, and component ablations. Keep model, agent instructions, corpus snapshots, context budgets and tool access equal; report actual tool adoption and failures, including intention-to-treat outcomes when an agent does not use the tool. Isolate persistent agent memory, hooks and caches across arms; historical transcripts contain benchmark memories from prior runs.

Decision criteria
MeasureWhat to include
Task qualityExecutable task success; evidence-set and source-line recall; exact-lookup regressions; natural-negative false evidence.
Agent costAll model input/output and cache tokens, rewrites, reranking, repeated searches and failure retries.
LatencyCold and warm p50/p95, process startup, encoding, query execution, result formatting and total agent duration.
Index lifecycleInitial build, model download/load where relevant, changed-file updates, lag, RAM, disk bytes and realistic query-count amortization.
UncertaintyPaired comparisons, repository-clustered confidence intervals, multiple agent runs, per-query-family failures and explicit abstention calibration.

Adopt a component when it improves the task-quality/cost tradeoff on held-out work without unacceptable exact-query regressions. Specify the allowed quality margin and resource ceilings before measuring. A faster lookup that causes another expensive agent round trip is a regression. A slower lookup can be worthwhile if it reliably avoids several searches or large file reads.

Suggested order: validate the FTS-first query-plan optimization, enforce the final payload cap and repair measurement; compact context and query variants; optional semantic candidate union; typed reverse relations and bounded multihop; then trained scheduling, learned sparse expansion or more elaborate indexes if the ablations justify them. Large graph summarization, token-level lossy code compression, and a custom ANN/WAND replacement are not justified as defaults by the evidence collected here.
