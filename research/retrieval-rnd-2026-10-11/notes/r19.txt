Research 19/25 — Incremental systems. Verified 2026-10-11.

Recommendation: extend existing content-addressed revision reuse into a demand-driven dependency graph for retrieval artifacts. This is a plausible engineering synthesis, not a newly proved algorithm or measured Lumen speedup. It reduces indexing/update cost; it does not itself improve vague-query recall.

Primary evidence:
1. Hammer, Phang, Hicks, Foster, “Adapton: Composable, Demand-Driven Incremental Computation,” PLDI, June 2014. Separates observers from incremental computations; a demanded computation graph recomputes affected outputs only when requested and permits reuse across contexts. This is a closer fit than eagerly regenerating every affected repository summary. https://matthewhammer.org/adapton/adapton-pldi2014.pdf ; author publication record: https://www.cs.umd.edu/~mwh/papers/hammer13adapton.html
2. McSherry, Murray, Isaacs, Isard, “Differential Dataflow,” CIDR, January 2013. Extends incremental computation to nested iteration and demonstrates changing graph computations such as strongly connected components. Transfer its signed insert/delete changes and versioned computation idea to postings, document-frequency counts and bounded graph neighborhoods; do not assume the whole engine is necessary. https://www.microsoft.com/en-us/research/publication/differential-dataflow/
3. Ahmad, Kennedy, Koch, Nikolic, “DBToaster: Higher-order Delta Processing for Dynamic, Frequently Fresh Views,” PVLDB 5(10), 2012, pp.968–979. Materializes queries and higher-order deltas, with a cost-based choice between maintenance and reevaluation. The authors explicitly identify cases where aggressive incrementalization loses. Useful lesson: materialize frequently used retrieval joins, not every conceivable cross-file relationship. https://vldb.org/pvldb/vol5/p968_yanifahmad_vldb2012.pdf

Concrete Lumen adaptation (proposed):
Maintain immutable nodes for source revisions → parsed chunks/symbols → sparse features/embeddings → module summaries/graph neighborhoods. Key each derived artifact by transform/parser/model/prompt version plus its exact ordered input identities and configuration, including path-sensitive inputs. Record source provenance, not merely semantic similarity. On edits, publish cheap lexical postings and signed statistics deltas immediately; dirty dependent semantic artifacts and recompute those demanded by candidates. Exact unchanged input identities permit reuse across branches/worktrees. Preserve a fresh lexical candidate route while semantic artifacts are dirty, so stale summaries never become the sole exclusion gate. Generated summaries are navigation aids; final evidence is original current source.

Detection is separate from reuse: hashing content avoids recomputation after identity is known, but does not detect edits without reading/statting/events. A durable event cursor and debounced dirty-path queue reduce routine full-tree hashing. Events remain hints: loss/overflow/restart or an uncertain cursor requires reconciliation; periodic full content audit is the correctness backstop. Deletes must retract postings and memberships; renames update path-sensitive artifacts; branch changes atomically publish a new membership snapshot and reuse surviving revision objects. Bound promises: asynchronous reconciliation cannot guarantee immediate freshness after an undetected event loss. Never advertise content hashes alone as O(changed-files) edit detection.

Experiment: replay real editing traces plus adversarial rename/delete, branch switches, equal-size timestamp-preserving edits, dropped events and restart. Compare current TTL full hashing, event-assisted reconciliation, eager dependencies, and demanded dependencies. Measure bytes read, CPU, p50/p95 update-to-searchable time, query p95, memory, embedding/summary tokens and stale-hit/deletion errors against a full-rebuild oracle. Vary repository size and edit fraction. Require output membership/statistics equivalence after reconciliation; report freshness during faults separately. Biggest expected win: large repositories, localized edits and expensive summaries. Broad dependency fanout or infrequent queries may erase it.
