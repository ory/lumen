R08/25 — Index-time expansion and context preservation (2026-10-11)

Recommendation: first benchmark deterministic context fields; then selectively add source-grounded generated intent descriptions. Context restoration and vocabulary expansion solve different failures, and their incremental value must be measured separately. Late chunking is a promising dense-retrieval ablation, not a proven universal winner.

Verified primary evidence (full methods/results inspected):

1. Gospodinov, MacAvaney, Macdonald, “Doc2Query–: When Less is More,” first submitted 2023-01-09; inspected revision 2023-02-27. https://arxiv.org/html/2301.03266
   Doc2query generates plausible queries from documents before indexing. This study filters generated queries using relevance models because some generated questions cannot be answered by their source. On MS MARCO, 80 generated queries plus ELECTRA retaining 30% increased Dev RR@10 from 0.279 to 0.323, reduced mean retrieval from 30 to 23 ms, and index size from 1.41 to 0.95 GB. These are improvements over unfiltered expansion: plain BM25 remained faster, 5 ms and 0.71 GB. DL19/20 gains were not statistically significant. Filtering adds indexing work; generator probabilities did not filter effectively. The actionable result is to cap and validate expansion, not append unlimited synthetic text.

2. Günther et al., “Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models,” first submitted 2024-09-07. https://arxiv.org/html/2409.04701
   Encode the document/macrochunk jointly, then mean-pool token embeddings separately inside small evidence spans. This preserves cross-span references without generating text or adding query-time vectors. Table 2 averages across three models/four small BEIR datasets: fixed-size chunking nDCG@10 52.2→54.0; sentence boundaries 52.4→54.3. Strongest benefits occur for small chunks with useful surrounding context. Unrelated surrounding text can hurt; the paper explicitly finds no benefit on synthetic needle/passkey cases. Comparison with Anthropic contextual embeddings is only a tiny illustrative example, not a general head-to-head benchmark. Requires access to token embeddings and appropriate long-context models; document/macrochunk changes require re-encoding all dependent spans.

3. Anthropic, “Introducing Contextual Retrieval,” 2024-09-19. https://www.anthropic.com/engineering/contextual-retrieval
   Vendor-authored engineering study, not independent peer-reviewed validation. A model sees whole document plus target chunk, generating 50–100 tokens of chunk-specific context for both BM25 and dense indexing. Across tested domains including codebases, reported top-20 failure falls 5.7%→2.9% (49% relative, 2.8 percentage points), and to 1.9% with reranking. Generic document summaries showed limited gains. These results combine contextual dense and lexical retrieval and cannot establish the isolated value of generated context versus cheap headers/signatures, nor agent-task completion gains. Historical cost figures should not be treated as current pricing.

Proposed Lumen design (engineering inference, not established result):
Store raw source spans separately from retrieval-only fields. Deterministic fields comprise path, document title/heading ancestry, language, enclosing class/function signature, relevant type names, and original doc comments. Avoid blindly copying whole-file metadata into every span. Optional generated fields contain 1–3 concise answerable intents/aliases and resolved referents, with exact source-span provenance. Generate solely from source and enclosing context; never use test queries, answers, issue titles serving as evaluation queries, or relevance labels. Gate generated fields with independent source-relevance checks, token budgets, and field weights; return original evidence plus visibly distinct metadata, never synthetic text as authoritative evidence.

Version by source hash + enclosing-context hash + parser/model/prompt version. Recompute descendants when a parent heading/signature changes; regenerate document-wide context if any supplying source changes. Permit foreground lexical search immediately while enrichment runs asynchronously. Index-time economics should include initial generation, edits and invalidation, storage, and number of subsequent queries: amortized extra cost/query = total enrichment/update cost divided by observed queries before invalidation.

Falsifiable experiment:
Freeze repositories/documents; collect independently authored paraphrase, pronoun-dependent, exact-identifier, and misleading-neighbor queries. Compare raw BM25; BM25+deterministic fields; plus filtered generated context; dense early versus late chunking with identical evidence boundaries. Hold tuning repositories out from test. Measure span recall at fixed 2k/4k returned-token budgets, nDCG, agent completion/tool calls, p50/p95 latency, index bytes, and update cost. Reject generated enrichment unless it beats deterministic fields on held-out approximate queries with paired confidence intervals, preserves exact-identifier quality, and improves amortized end-to-end cost. Include frequent-edit workloads; otherwise offline gains can hide impractical regeneration expense.
