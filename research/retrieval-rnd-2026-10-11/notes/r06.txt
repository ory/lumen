Research 06/25 — dense semantic retrieval and compression

Recommendation: retain Lumen's fielded BM25 and AST chunks, but test an independent dense candidate channel for vocabulary-mismatched queries. Dense reranking of only BM25 hits cannot recover documents BM25 never retrieved. Fuse candidates, preserving an exact-symbol/identifier route. This is an engineering hypothesis, not a measured Lumen result. For a realistic code-oriented challenger choose CodeXEmbed-400M; for multilingual prose, separately evaluate Arctic-Embed 2.0-M. Avoid adopting a multi-billion-parameter encoder as the default local CLI dependency before measuring total session economics.

Primary evidence (verified paper text)

1. CodeXEmbed: A Generalist Embedding Model Family for Multilingual and Multi-task Code Retrieval. Initial November 2024; inspected revision August 8, 2025. https://arxiv.org/html/2411.12644v3
The paper trains code/text retrieval across 12 programming languages and varied text-to-code, code-to-code, and mixed tasks. Its 400M general-training model reports CoIR average nDCG@10 61.89 versus CodeSage-large-v2 64.18; the 400M in-domain variant reaches 68.42. This distinction matters: benchmark-adapted scores should not be presented as unseen-repository performance. The paper's BEIR table reports 58.34 versus BM25 41.7, but the dense model loses substantially on Touche-2020 (20.18 versus 36.7). Its training description includes text retrieval datasets, so do not claim a universal zero-shot gain. These results make 400M a credible challenger, not proof of superiority on Lumen's tasks. Raw FP16 weights alone would require approximately 800 MB by parameter arithmetic; runtime memory is higher.

2. Arctic-Embed 2.0: Multilingual Retrieval Without Compromise. December 3, 2024. https://arxiv.org/html/2412.04506v1
Matryoshka training supports 256-dimensional vectors. The medium model's MTEB retrieval nDCG@10 changes from 0.554 at 768 dimensions to 0.549 at 256, while CLEF changes from 0.534 to 0.522. The table lists 113M NON-EMBEDDING parameters, not total weights. Its multilingual evidence is prose retrieval, not code or identifiers. The authors explicitly contrast Wikipedia-based MIRACL with out-of-domain news-based CLEF: language/domain benchmark choice changes apparent winners. Scalar quantization can further reduce storage; its local recall impact needs measurement.

3. 2D Matryoshka Training for Information Retrieval. November 26, 2024. https://arxiv.org/html/2411.17299v1
This reproducibility study finds a material caveat: a flexible model truncated across dimensions/layers does not outperform separately trained small models across retrieval configurations. Conventional dimension-only Matryoshka saves comparison/storage cost but preserves encoder cost. Layer truncation addresses encoding latency, yet must be trained and validated; the study's full-document/small-query encoder combination gives inconsistent improvements. Therefore “256 dimensions” does not imply cheap cold indexing or query encoding.

Cost and failure analysis (engineering deductions)

Charge cold startup/model load + embedding every changed chunk + index maintenance + query encoding + candidate search + downstream agent input tokens. Benchmark both cold and resident modes; warm vector lookup alone hides dominant work. For illustration, 100,000 vectors cost 307.2 MB at 768 float32 coordinates versus 25.6 MB at 256 int8 coordinates, excluding graph, IDs, scales, metadata, and any full-vector rerank copy. Compression does not eliminate model weights. Code/text domain training improves semantic matching but may blur exact identifiers, negation, numeric constraints, configuration keys, and similar-but-wrong functions. Document-only models are especially unproven on code, tables, and raw structured data.

Falsifiable experiment

Hold out entire repositories and collect genuine tasks stratified into identifiers, paraphrases with no shared content words, multilingual prose, and mixed code/documentation. Compare identical chunking/token budgets for BM25, dense-only, union+fusion, and routed fallback. Include identifier renaming and semantically related decoys. Measure evidence Recall@20, nDCG@10, successful agent task completion, delivered context tokens, cold-index CPU seconds, incremental-update cost, resident RAM, and p50/p95 end-to-end latency. Accept dense addition only if the confidence interval shows a meaningful mismatch-recall/task-success increase without an unacceptable exact-lookup regression, and measured agent-time/token savings amortize embedding cost over realistic session query counts. No reviewed paper establishes that break-even point for Lumen.
